# 코딩 규칙 및 금지 사항

## 하지 말아야 할 것

- `any` 타입 사용 금지
- `useEffect`로 데이터 페칭 금지 → Server Component 또는 Server Action 사용
- default export 금지 → Named export 사용 (Next.js가 요구하는 `page`·`layout`·`loading`·`error`·`not-found`·`proxy` 등 규약 파일은 예외)
- API Route 신규 생성 금지 → Server Action 사용
- 컴포넌트 안에서 Supabase 클라이언트를 직접 생성 금지 → `@/lib/supabase/server`(서버) 또는 `@/lib/supabase/client`(브라우저)의 `createClient()`를 import해서 사용
- 인라인 스타일 금지 → Tailwind 클래스 사용
- `console.log` 커밋 금지
- 요청 범위 밖의 기존 파일 수정 금지 — 지침은 신규 파일 또는 직접 수정 요청된 파일에만 적용

---

## 프로젝트 원칙

1. **Next.js 기본 기능과 브라우저 표준으로 먼저 해결**하고, 안 될 때만 패키지를 추가한다.
2. shadcn/ui 컴포넌트는 **실제로 쓰는 것만 하나씩** 추가한다.
3. 권한은 화면(버튼 숨김)과 DB(RLS) **양쪽에서** 막는다.

## 네이밍

- 컴포넌트 파일은 PascalCase (예: `SpeakerCard.tsx`)
- 일반 파일은 kebab-case (예: `format-date.ts`)
- 상수는 UPPER_SNAKE_CASE
- shadcn/ui가 생성한 `src/components/ui/*` 파일은 생성된 이름(kebab-case) 그대로 둔다

## 컴포넌트

- 한 파일당 하나의 주요 export
- 관련 타입은 같은 파일에 정의
- 기본은 Server Component, 인터랙션이 필요할 때만 `'use client'` — 클라이언트 경계는 최대한 아래(잎) 쪽에 둔다

## 스타일링

- Tailwind className 조합 시 `cn()` (`@/lib/utils`) 사용
- 모바일 기본 → `md:` → `lg:` 순서로 작성
- 모션은 Tailwind transition + `IntersectionObserver`로 만들고, 반드시 `motion-reduce:`로 끌 수 있게 한다
- 누르는 영역 최소 44×44px, 본문 글자 16px 이상(글 읽기 화면 17px), 명도 대비 4.5:1 이상

## 데이터 · 폼

- 데이터 변경은 Server Action으로 한다
- 입력값 규칙은 zod 스키마 하나로 정의해 **화면과 서버 양쪽**에서 사용 (화면설계서 9-2와 문구까지 일치시킬 것)
- Server Action에서도 권한을 다시 확인한다 — 화면에서 버튼을 숨긴 것만 믿지 않는다
- 데이터를 등록·수정하면 관련 캐시 태그를 갱신한다
- 목록 상태(회차·페이지·검색어·팝업)는 URL 검색 파라미터로 관리

## 리치 텍스트 (Tiptap)

- 본문은 **JSON으로 저장**하고, 출력할 때 같은 확장 구성으로 HTML을 만든다
- 링크는 `http(s)`만 허용
- 본문 이미지는 Supabase Storage에 올리고 주소만 저장
- Q&A **질문**은 일반 텍스트 (에디터 사용 안 함)

## 날짜 · 숫자

- `Intl.DateTimeFormat` + `timeZone: 'Asia/Seoul'`
- 날짜 `2026.11.04`, 포럼 일시 `2026.12.05(토) 14:00`, 회차 `제27차`, 조회수 `1,234`

## 보안

- JSON-LD 등 `<script>`에 데이터를 넣을 때 `JSON.stringify`를 그대로 쓰지 않는다 (`</script>` 삽입 XSS)
- `dangerouslySetInnerHTML`은 Tiptap이 만든 HTML과 안전 직렬화한 JSON-LD에만 쓴다
- 비밀 키(service_role 등)는 클라이언트 코드·`NEXT_PUBLIC_` 변수에 넣지 않는다
- 로그인 실패·비밀번호 재설정 안내는 가입 여부를 드러내지 않는 문구로

## 일부러 쓰지 않는 라이브러리

| 용도                                  | 대신 쓰는 것                              |
| ------------------------------------- | ----------------------------------------- |
| 상태 관리 (Zustand, Redux 등)         | `useState` + URL 검색 파라미터            |
| 서버 상태 (React Query, SWR)          | Server Components + Cache Components      |
| 애니메이션 (Framer Motion 등)         | Tailwind transition                       |
| 슬라이더 (Swiper 등)                  | CSS `scroll-snap`                         |
| 날짜 (dayjs, date-fns 등)             | `Intl.DateTimeFormat`                     |
| 지도 SDK                              | 네이버·카카오 지도 앱 링크                |
| HTML 정화 라이브러리                  | Tiptap JSON → 허용한 확장으로만 HTML 생성 |
| 게시판·포럼 앱 (Flarum, Discourse 등) | 직접 구현                                 |

새 패키지를 추가해야 할 때는 이유를 `docs/context-notes.md`에 남긴다.

## 에이전트 코드 작성 지침

LLM의 흔한 코딩 실수를 줄이기 위한 행동 지침. Andrej Karpathy의 관찰에서 도출됨.

**트레이드오프** — 이 지침들은 속도보다 신중함을 우선한다. 사소한 작업은 판단해서 적용할 것.

### 1. 코딩 전에 먼저 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현 전에 아래를 확인할 것.

- **코드 수정 전에 반드시 실제 파일을 먼저 읽는다.** 계획이나 문서만 보고 수정하지 않는다. 파일의 실제 구조와 의존관계를 확인한 후 작업을 시작한다. 다른 파일·문서를 "참고"하라는 요청을 받으면 그 파일을 실제로 열어 읽는다.
- 가정을 명시적으로 서술한다. 불확실하면 질문한다.
- 여러 해석이 가능하면 제시한다 — 조용히 선택하지 않는다.
- 더 단순한 접근이 있으면 말한다. 필요하면 반론을 제기한다.
- 불분명한 부분이 있으면 멈춘다. 무엇이 혼란스러운지 명시하고 질문한다.

### 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드는 없다.**

- 요청받은 것 이상의 기능은 추가하지 않는다.
- 단일 사용 코드에 추상화하지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 추가하지 않는다.
- 불가능한 시나리오에 대한 에러 처리를 하지 않는다.
- 200줄로 작성했는데 50줄로 가능하다면 다시 작성한다.

스스로 물어볼 것. "시니어 엔지니어가 이걸 보고 과하게 복잡하다고 할까?" 그렇다면 단순화한다.

### 3. 외과적 변경

**반드시 필요한 곳만 건드린다. 내가 만든 지저분함만 정리한다.**

기존 코드를 수정할 때는 아래를 지킨다.

- 인접한 코드, 주석, 포맷을 "개선"하지 않는다.
- 망가지지 않은 것을 리팩토링하지 않는다.
- 내 스타일과 달라도 기존 스타일을 따른다.
- 관련 없는 dead code를 발견하면 언급은 하되 삭제하지 않는다.

내 변경으로 인해 orphan이 생긴 경우는 아래와 같이 처리한다.

- 내 변경으로 인해 사용되지 않게 된 import/변수/함수는 제거한다.
- 기존에 있던 dead code는 요청받지 않으면 건드리지 않는다.

테스트 기준은 하나다. 변경된 모든 줄은 사용자의 요청으로 직접 추적 가능해야 한다.

### 4. 목표 중심 실행

**성공 기준을 정의한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 전환할 것.

- "유효성 검사 추가" → "잘못된 입력을 넣었을 때 의도한 오류가 나는지 확인한다"
- "버그 수정" → "버그를 재현하는 방법을 먼저 찾고, 수정 후 재현되지 않는지 확인한다"
- "X 리팩토링" → "리팩토링 전후 동작과 검증 명령 결과가 같은지 확인한다"

여러 단계 작업이라면 간략한 계획을 먼저 서술할 것.

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

명확한 성공 기준이 있어야 독립적으로 반복할 수 있다. "작동하게 해줘" 같은 기준은 매번 명확화가 필요하다.

### 5. 한국어 출력 시 문장 끝에 콜론 금지

**한국어 문장은 마침표로 끝낸다. 콜론으로 끝내지 않는다.**

사용자가 한국어로 작성하면 출력도 한국어로 한다. 이 규칙은 대화 응답과 문서(`AGENTS.md`, `docs/`) 모두에 적용한다.

- 다음 줄이 목록이나 예시여도 문장을 `:`로 끝내지 않는다.
- 영어 문서로 훈련된 LLM은 콜론 습관을 한국어에도 적용한다. 주의할 것.
- 한국어 문장 종결어미는 `.`, `?`, `!`이어야 한다 — `:` 가 아니다.
- 코드, key-value 쌍, 레이블 내부의 콜론은 허용된다. 문장 끝에는 금지다.

### 6. 새 파일 상단에 한국어 한 줄 주석

**새 소스 파일을 만들 때 첫 줄에 파일의 역할을 설명하는 한국어 한 줄 주석을 작성한다.**

- TypeScript/JavaScript는 `// 발제자 상세 팝업을 보여주는 컴포넌트` 형식
- SQL은 `-- 포럼 회차 정보를 저장하는 테이블` 형식
- 필수 디렉티브(`'use client'`, `'use server'`) 바로 아래에 위치시킨다.
- 설정 파일(`*.config.ts`, `package.json` 등)과 shadcn/ui CLI가 생성한 `src/components/ui/*` 파일은 생략한다.
- 이 규칙을 정하기 전에 만든 파일(`src/lib/supabase/*`, `src/proxy.ts` 등)에는 소급 적용하지 않는다.

이유는 이렇다. 에이전트는 전체 코드베이스가 아닌 파일 단위로 선택적으로 읽는다. 한 줄짜리 한국어 헤더가 있으면 다음 세션(사람이든 에이전트든)이 전체 파일을 다시 읽지 않아도 즉시 맥락을 파악할 수 있다.

### 7. 계획 + 작업 목록 + 컨텍스트 노트

**사소하지 않은 작업이라면 코딩을 시작하기 전에 세 가지를 먼저 정리한다.**

- **계획** — 무엇을 왜 만드는지.
- **작업 목록** (`docs/todo.md`) — 체크박스 형태의 구체적인 작업 목록. 진행하면서 체크한다. 분량이 커지면 `docs/features/<기능>.md`로 분리한다.
- **컨텍스트 노트** (`docs/context-notes.md`) — 작업 중 내린 결정과 그 이유. 지속적으로 추가한다.

두 파일은 이렇게 나눠 쓴다.

- `todo.md`에는 **무엇을 할지만** 적는다. 이유와 배경은 `context-notes.md` 또는 `docs/features/`에 적는다.
- `todo.md` 항목을 끝내면 체크하고, 그 과정에서 내린 결정이 있으면 `context-notes.md`에 이유를 한 줄 남긴다.
- 기획 결정과 포럼에서 받을 자료는 노션 화면설계서 11-2에서 관리하고, `todo.md`에는 개발 작업만 둔다. 같은 항목을 양쪽에 두지 않는다.

사용자가 계획만 주고 코딩을 시작하라고 하면 먼저 물어볼 것. "작업 목록과 컨텍스트 노트를 먼저 정리할까요?" 다음 세션 — 내 것이든 다른 누군가의 것이든 — 은 모든 결정을 다시 유도하지 않고 이어받기 위해 노트가 필요하다.

### 8. 완료 표시 전에 검증 실행

**코드를 건드렸다면, "완료"라고 말하기 전에 검증 명령을 실행한다.**

```bash
npm run lint
npm run typecheck
npm run build
```

- 모두 통과하면 결과를 보고한다. 실패하면 수정하고 다시 실행한다.
- 테스트 도구는 추후 추가 예정이다. 추가되면 이 목록에 테스트 명령을 더한다.
- "끝", "완료", "다 됐어" 신호를 기다리지 말고 먼저 실행한다.

이 단계는 LLM이 가장 자주 건너뛰는 단계다. 타협 불가로 취급할 것.

### 9. 에러는 추측하지 말고 읽을 것

**실제 에러/로그 줄을 읽는다. 기억에서 패턴 매칭하지 않는다.**

무언가 실패했을 때는 아래를 지킨다.

- 전체 에러 메시지와 스택 트레이스를 읽는다.
- 예상하는 내용이 아닌 실제 로그 출력을 확인한다.
- 원인을 확인하기 전에 "흔한 수정법"을 적용하지 않는다.
- 불분명하면 로그를 추가해서 상태를 확인한 후 수정한다. 확인용 로그는 커밋 전에 지운다.

이 단계는 "검증 실행" 다음으로 LLM이 가장 자주 건너뛰는 단계다. 에러 키워드로 추측하고 가장 최근에 봤던 패턴 수정법을 적용한다. 그렇게 한 줄짜리 버그가 세 파일 리팩토링이 된다.
